## Сервер хранилища (crs) и клиент-серверные ИБ

Проверено на живом сервере хранилища (Windows-служба crserver, репозитории
`cf` и `ext/Расширение1`):

- **нативно на Windows** — `storage = "tcp://localhost/cf"` (порт по
  умолчанию 1542; лицензия рабочей станции), 5+2 коммита;
- **из Docker** — `storage = "tcp://host.docker.internal/cf"` (хост-сервер
  виден через Docker Desktop), 5+2 коммита; контейнеру нужна лицензия
  (нативно на Windows — нет).

Клиент-серверная ИБ для выгрузки задаётся в `[gitsync]`
(`ib_connection = "/S<server>\\<ref>"` или `Srvr="...";Ref="...";` +
`ib_user`/`ib_pwd`); для `xml_backend = "ibcmd"` — параметры СУБД
(`ibcmd_dbms` и т.д.). Подробности — [sync-config.md](sync-config.md).

## Выводы

- **gitsync/configurator+configurator** — самый быстрый вариант для
  конфигураций (~2× к tool1cd-движку): инкрементальный дамп + инкрементальный
  EDT-импорт; требует конфигуратор и лицензию.
- **tool1cd-движок** — без лицензии и конфигуратора, единая кодовая база
  Windows/Docker; расширения через depot v100 (наш upstream PR #295).
- **gitsync + расширения** — работают через `-Extension` (включая
  `gitsync init -e`), полный дамп на версию; чуть медленнее, но в одном
  стеке с конфигурацией.
- **storage_backend=ctool1cd** (плагин tool1CD) — не проверялся в замерах:
  доступен только на Windows (виндовые бинарники плагина; в Linux нужен wine,
  который не используется); расширения плагин не поддерживает.
- Замеры на мини-конфигурации (fixtures): на реальных больших конфигурациях
  доли фаз сдвигаются в сторону EDT-импорта — абсолютные числа масштабируются,
  относительный порядок вариантов ожидаемо сохраняется.

Методика: `.storage-sync-stats.json` (по-версионные тайминги фаз),
свежий worktree на каждый прогон, один и тот же host. Повторные запуски
различаются <5%.
